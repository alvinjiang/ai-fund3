# AI Fund v3 — Research Pipeline

Status: Approved by PM 2026-07-07. Companion to 02-DOMAIN-MODEL.md (Run entity).

The pipeline formalizes the manual workflow that produced the PM's gold-standard
reports: a strong author pass followed by verification passes from *different* models
instructed to **verify, correct, and re-reason — not to critique**. The Yakult 2267
report artifacts define the output contract.

## 1. Stage contract

Every stage — regardless of run type or substrate — has the same shape:

**Inputs (workspace):**
- The ticker's dossier checkout (fresh branch per run: `run/<id>`).
- `task.md` — generated by the orchestrator from the run type, stage role, doctrine,
  and trigger context (e.g. the tripwire that fired, the PM's question).
- `doctrine/` (read-only mount): core rules, section prompts, role instructions,
  lessons, templates.
- Tool access per substrate (see 05-SYSTEM-ARCHITECTURE.md): market-data service,
  web search, filesystem in workspace.

**Outputs:**
- Updated workspace files (dossier edits, report artifacts).
- `stage_result.yaml` — machine-readable summary, schema-validated by the runner:

```yaml
status: completed          # completed | blocked | nothing_material
changes: [ ... ]           # what was changed/produced, one line each
corrections:               # only verify/data-check roles
  - target: "report-content.md#comps"
    was: "Meiji price ¥4,027"
    now: "¥3,763 (close 2026-06-09, source: ...)"
    attributed_stage: 1    # whose output contained the error
predictions:               # to register in the ledger
  - kind: target_price
    value: 2900, currency: JPY, horizon_date: 2027-06-30, confidence: 0.65
escalate:                  # optional
  reason: "TP change exceeds ±10%, contributor cross-check required"
disagreement:              # optional, cross-check stages
  stance_vs_lead: "..."
  material: true
lead_change_proposal:      # optional, lead_review stages
  proposed_house: gemini
  rationale: "..."
```

**Deterministic gates between stages (runner-enforced, no LLM):**
- `stage_result.yaml` present and schema-valid — a stage that "answers in prose" fails.
- Required artifacts exist for the role (e.g. author stage of an initiation must
  produce `report-content.md`, workbook, `build_workbook.py`, references).
- Report↔workbook reconciliation check for report-producing stages: headline figures
  extracted from the report must match workbook cells (port of the Yakult
  reconciliation discipline; implemented as a script, not a model).
- Recommendation/confidence fields must come from the stage output — never
  synthesized by code when missing (v2 lesson: fabricated "Neutral/50%" footers).
  Missing ⇒ stage fails and retries with the omission named in the retry prompt.

## 2. Run type definitions

### 2.1 `initiation` (heavy; the front door)

Trigger: PM `/propose <ticker> [lead=<house>]`. Default lead: PM-specified (cheap
start, per PM decision); if unspecified, orchestrator suggests based on track record.

| # | Role | House | Substrate |
|---|---|---|---|
| 1 | author | lead | harness |
| 2 | verifier | contributor A | harness |
| 3 | verifier | contributor B | harness |
| 4 | finalizer | lead | harness |

- **Stage 1 — author**: full report per doctrine (all section prompts), producing the
  Yakult-contract artifact set: `report-content.md`, workbook (single computed layer)
  + `build_workbook.py`, references with retrieval dates, market-data notes, plus
  **draft dossier files** (dossier.md, valuation.md, tripwires.yaml).
- **Stages 2–3 — verifiers** (different houses): the proven prompt family — *"check
  every reference, verify all data and correct any mistakes and omissions, write your
  own reasoning and check workings."* Each pass edits the artifacts in place to the
  best corrected state and appends to the corrections log. Stage 3 additionally
  re-pins the subject price fresh and re-runs reconciliation. Verify-pass count is
  configurable per run (default 2, min 1 for watch-tier initiations if PM wants
  cheaper).
- **Stage 4 — finalizer**: applies the HTML template, renders PDF, produces the final
  reconciliation table, completes dossier files, registers predictions, writes the PM
  decision summary (recommendation, TP, horizon, entry point, scenarios, confidence,
  corrections count).
- Run ends `waiting_pm`. PM decides: **active / watch / reject** (with optional
  notes). On accept: dossier branch merges to main; predictions become `open`; tier
  set; monitoring starts; ticker channel created and report delivered there (PDF +
  summary). On reject: branch retained, coverage `rejected`.

### 2.2 `deep_review` (heavy)

Trigger: earnings release (from the data-source calendar), quarterly timer for names
without recent reviews, or PM.

| # | Role | House | Substrate |
|---|---|---|---|
| 1 | author (update) | lead | harness |
| 2 | verifier | rotating contributor | harness |

Lead refreshes the dossier against new filings/results: updated valuation, revised
predictions (superseding old ones), tripwires refreshed, event note in `events/`.
Verifier corrects. Material stance/TP changes escalate to PM notification with diffs
("what changed since last review" is computed from dossier git diff).

### 2.3 `event_analysis` (medium)

Trigger: tripwire hit or monitor escalation; or PM (`/analyze <ticker> <question>`).

Single lead stage (harness; may run api-substrate for minor severity), required to:
assess against the thesis, update dossier (or explicitly declare nothing material),
adjust predictions if warranted, and produce a PM-facing note with workings.
**Auto cross-check rule:** if |ΔTP| > 10%, stance changes, or a `thesis`-severity
tripwire fired, a contributor cross-check stage is appended automatically. A material
disagreement is recorded and surfaces to the PM verbatim from both sides (structured
disagreement replaces the v2 debate engine).

### 2.4 `monitor_tick` (minimal; mostly not an LLM)

Trigger: per-exchange session schedule (pre/post-market), tier-dependent frequency
(active: every session; watch: daily/weekly, news-only).

1. **Code:** fetch prices via the market-data service; evaluate price/level tripwires,
   entry zones, stops; compute move vs thresholds.
2. **Code:** fetch news (ported v2 multi-source fetchers + dedup) for the ticker.
3. **Cheap model (single call):** score fetched items against the ticker's
   `tripwires.yaml` text and thesis one-liner: `{item, tripwire_id | none,
   materiality, one_line_reason}`.
4. **Code:** escalation policy — `thesis` severity or high materiality ⇒ spawn
   `event_analysis`; `info` ⇒ post a digest line; nothing ⇒ silence. Digests are
   threshold-gated (port of v2 noise suppression) — the PM's channels stay quiet
   unless something is worth reading.

### 2.5 `pm_query` (light)

Trigger: mention/DM in a ticker channel or CLI question. Runs on the lead house's
light model via API substrate with the dossier as context; answers must cite dossier
state (stance, TP, as-of date) and say when the dossier is stale rather than
improvise. May offer to spawn a run ("want a deep review?") but never spawns heavy
work without PM confirmation. Notable exchanges are curated into `queries/`.

### 2.6 `lead_review` (medium)

Trigger: PM request, or automatic candidacy flag when a lead's track record breaches
thresholds (e.g. 3 consecutive scored misses, or corrections-received rate ≫ roster
median — thresholds configurable).

Contributors (api or harness substrate) review the dossier, the lead's predictions vs
outcomes, and corrections attribution, then each files keep/change with rationale via
`stage_result.yaml`. The orchestrator aggregates into a recommendation. **PM approves
any change** (v1 has no auto-switching). On change: new lead inherits the dossier;
the handover is logged; old lead's open predictions remain attributed to it.

### 2.7 `distillation` (Claude meta; monthly or PM-triggered; harness substrate)

Input: all corrections logs, scored misses, and `lessons.md` entries since the last
distillation. Output: a proposed amendment to `doctrine/lessons/global.md` (and
optionally role/section prompts) as a **git branch + PR-style diff** the PM approves.
Also produces a system-health memo: per-house calibration, pipeline failure patterns,
cost anomalies. This formalizes the "Further notes from past mistakes" loop the PM
ran by hand in Equity-Research-Prompts.

## 3. Doctrine layout

Seeded from `Equity-Research-Prompts_2026-06-05.md` (split, not rewritten — the
content is proven):

```
doctrine/
  core.md                 # references, currencies, calculations, price-pinning,
                          # no-placeholder, FX, reconciliation, terminology rules
  sections/               # 14 section prompts (company_overview.md, bull_bear.md, ...)
  roles/                  # author.md, verifier.md, data_checker.md, finalizer.md,
                          # monitor.md, cross_check.md, lead_review.md, distiller.md
                          # data_checker: optional insertable cheap pass (numbers-only
                          #   re-verification); not in any default stage graph.
                          # lead_review.md is the ROLE prompt used by stages inside
                          #   the lead_review RUN TYPE (§2.6) — same name, two layers.
  lessons/global.md       # "past mistakes" rules; amended only via distillation PRs
  report/                 # full-report spec: stat block, naming (NAME_SYM_EXCH-YYYYMMDD),
                          # corrections-log requirement, template usage
  templates/              # ironclad HTML template, workbook conventions
```

Role prompts encode the division of labour, including the doctrine's own rule to use
smaller/faster models for bulk data retrieval *within* a harness session (the harness
agent may spawn its own cheap sub-lookups where its CLI supports it).

## 4. Cost envelopes (design targets, tuned in Phase 2)

| Run type | Envelope/run | Expected volume |
|---|---|---|
| initiation | $10–40 (3–4 harness stages) | ~1–2/week |
| deep_review | $5–20 | ~25 names × quarterly ≈ 2/week |
| event_analysis | $1–10 | bursty; few/week |
| monitor_tick | <$0.05 (one cheap call) | ~50/day active + watch |
| pm_query | <$0.20 | ad hoc |
| distillation | $5–15 | monthly |

Per-house daily caps and per-run caps enforce these (ported cost tracker, extended to
harness stages). A run that hits its cap pauses `waiting_pm` rather than silently
degrading quality.
